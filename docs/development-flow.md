# ここいこの開発手順

参照元：[再現性の高いAI駆動開発手順](codex_reproducible_ai_development_workflow.md)。
原本は変更せず、本書にプロジェクト固有の運用をまとめる。
要件は[要件定義書](kokoiko-requirements.md)、判断は[decisions](decisions.md)、
実行方法は[verification](verification.md)、タスクは[TASKS](../TASKS.md)を参照。

## タスク開始

1. 作業場所・Gitルート・branch・statusと、適用されるAGENTS／overrideを確認する。
2. 未コミット変更・未追跡ファイル・他担当の編集を把握し、自分の変更と分ける。
3. [テンプレート](tasks/TEMPLATE.md)でGoal、対象要件ID、対象外、制約、変更ファイル、依存、Done、Verification、担当を定義する。
4. 初回・仕様全体変更では要件全体、通常は対象IDと節 → 関連docs → コードを読む。
5. 不足と再利用部品を調査し、実装案・影響・未決定事項を示して方針を確認する。

未確定の受入条件・権限・設計は採用確認してから実装する。承認済みの作業範囲は引き継ぎ、
毎回同じ確認を要求しない。今回の文書整備は作成・更新まで許可されている。
機能実装・依存や設定・DB・CI・commit／push／merge／deployは今回の範囲外。

## 1タスクの流れ

**タスク定義 → 調査 → 方針確認 → 実装 → 検証・修正 → 自己レビュー
→ 別AIまたは人間のレビュー → CI → 人間が判断してマージ**

- 1機能全体を1依頼にせず、画面・処理・状態など検証できる小単位へ分ける。
- 実装は対象ファイルへ限定し、既存設計・命名・共通部品を再利用する。
- 文書のみのタスクでは「実装」を文書編集として扱い、不要なアプリ検証を追加しない。
- 変更に合う検証を実行し、失敗を調査して今回の原因なら修正・再確認する。
- 自己レビューでは要件、不要な変更、重複、型、エラー、アクセス制御、回帰を確認する。
- 別レビューの指摘は実装担当へ戻し、修正後に差分・検証を再提示する。
- CI workflowはCI-02で追加した。GitHub上で未実行なら「未実行」と報告する。
- CI実行後は対象commitの結果を確認する。失敗時は原因を修正して再確認する。
- タスク完了・自動検証・操作確認・レビュー・CI・mainへのマージは別の状態で記録する。
  旧TASKSの完了基準を引き継ぎ、未検証・未マージをリリース済みと扱わない。

## バグと再発

修正前に再現条件・期待と実際・対象環境を記録し、可能なら意味のある回帰検証を用意する。
修正後は同じ条件で再確認し、関連する既存検証も行う。
同じミスを繰り返す場合は、docsの追記だけでなくテスト・lint・CI等の検出を検討する。
今回の文書整備のためにテスト基盤を新設するものではない。

## Gitと既存変更の保護

- `main`へ直接大規模変更せず、機能・修正ごとにbranchを使う。commitは小さな意味の単位。
- 今回はbranch切替・worktree作成・stage・commit等を実施しない。
- 既存のdirty状態で旧手順のpull／switch／一括addを機械的に実行しない。
- 未コミット変更は削除・巻き戻し・一括ステージしない。操作前に担当と対象を確認する。
- README・AGENTS等は有効な内容を保って差分で統合する。承認を避けるために指示を消さない。
- `.env.local`、認証情報、APIキー、秘密鍵をcommitせず、環境変数は名前・用途だけ扱う。
- 変更後はtracked diffだけでなく未追跡ファイルの本文も読む。
  通常の`git diff`に新規未追跡ファイルが出ないことに注意する。

## 並列作業とレビュー担当

- 初期の共通文書整備は1つのAgentが担当する。今回は本会話のAgentが単独担当。
- 複数Agentによる実装は原則Agentごとにbranchとworktreeを分け、担当・依存・境界を先に決める。
- Herdrのタブを分けただけで、作業ファイルやGitブランチが分離されたとは扱わない。
- 同じ作業ディレクトリで複数Agentがbranchを切り替えない。
- 同じファイルを同時編集しない。共有の型、共通UI、migration、lockfileは担当を1つに決める。
- APIと型の契約を先に合意し、独立した仕事だけを並列化する。
- worktreeが別でも統合時に同じファイルを変更するなら、無条件に並列可とはしない。
- TASKS・decisions等の共通記録も担当を1つにし、各担当の結果を受け取って統合する。
- レビュアーはbranchとcommit、または固定した未コミット差分・新規ファイル一覧を指定して読む。
  実装者のファイルへ勝手に修正を加えない。対象が変わったらレビュー範囲を更新する。
- 他Agentへの自動指示は設定・能力・許可を確認してから使う。
  今回の文書整備だけで他Agentを起動しない。別レビューは人間へ渡す。
