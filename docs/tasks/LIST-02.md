# LIST-02：複数リストで共有候補を分類する

作成日：2026-10-18。状態：実装中。担当：本Agent単独。
branch：`feat/shared-lists`。基準：`bbb8195`。F-03/04/05、N-02/03/04/06/07/10。

## Goal・採用範囲

ユーザーがQ-04への回答で「1候補を複数のリストへ入れられる」「削除時は候補・コメント・反応を残しリストだけ削除」を選択した。
D-008の通常管理を全員で行う方針を継続し、グループメンバー全員が作成・名前変更・分類の追加/解除・リスト削除を行えるようにする。
小さい仮定：リスト名は既存のグループ名と同じ80 Unicode文字以内・前後空白除去・空名不可。検索100文字、20件のページ送りを既存候補に合わせる。同名リストの禁止は導入しない。

## 実装・Done・検証

- `lists`と候補/リストの中間テーブルを追加する。所属RLS・列権限・複合FKでグループ間の結合と作成者/所属の改ざんを防ぐ。新しいRPCはSECURITY INVOKERで呼出者のRLSを適用する。
- 名前変更は比較元の名前が一致する場合に保存し、古い画面からの上書きを拒否する。作成はUUIDを使い再送で重複させない。
- 分類は1リストずつ希望状態を保存し、他リストの分類を丸ごと置き換えない。リスト削除は確認画面を経由し、カスケードは分類の結合行だけ。候補本体・コメント・反応は変更しない。
- リスト管理・名前検索・ページ送り、候補詳細での分類追加/解除、候補一覧のリスト/未分類絞り込み・既存条件との併用と復帰を実装する。本文のStreamingを維持する。
- SQLで匿名/非所属/別グループ/改ざん/同時編集の衝突/再送/削除後の保全/ページと件数を検証する。Action/取得/URLと既存回帰、lint・型・build、自己レビュー・CIを行う。
- 実Supabaseは接続済みツールで既存8件の履歴と未作成を確認後、`create_lists`を適用した。実version `20261017230707`へローカル名を同期。新テーブル2件のRLS、6関数、列権限、複合FK、migration履歴を読み取り確認した。ユーザーデータ・認証情報は読まない。
- 実ユーザーでの操作確認は最後にまとめる。外部API・依存更新・既存データ削除・退会/グループ削除・予定/写真・コメント編集は範囲外。
