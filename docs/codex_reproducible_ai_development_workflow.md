# Codexを使った再現性の高いAI駆動開発手順

## 0. この手順の目的

この手順は、Codexに「とりあえず実装して」と投げるのではなく、

- 毎回なるべく同じ品質で進める
- 大きな変更を一気にさせない
- Codex自身に確認・修正までさせる
- 人間は仕様や設計判断に集中する
- ミスが起きても次回以降に再発しにくくする

ことを目的とする。

基本の考え方は次の通り。

> 人間が「何を作るか・なぜ作るか・どこまでできれば完了か」を決め、  
> Codexが「調査・実装・テスト・修正」を担当する。

---

# 1. 開発を始める前に整えるもの

Codexを使う前に、リポジトリ側をある程度「AIが作業しやすい状態」にしておく。

最低限あるとよいものは次の通り。

```text
repository/
├── AGENTS.md
├── README.md
├── docs/
│   ├── architecture.md
│   ├── frontend.md
│   ├── database.md
│   └── specs/
├── src/ または apps/
├── tests/
└── package.json
```

すべて必須ではない。

重要なのは、

- どこに何が書いてあるか分かる
- 実行方法が分かる
- テスト方法が分かる
- Codexが迷ったときに調べられる

状態にすること。

---

# 2. AGENTS.mdは短くする

AGENTS.mdには、プロジェクト全体の詳細を全部書かない。

役割は「案内板」にする。

例：

```md
# AGENTS.md

## 基本方針

- 既存の設計・命名規則を優先する
- 必要以上に広い変更をしない
- 変更後は関連テストを実行する
- public APIを変更する場合は理由を説明する

## Architecture

設計方針は `docs/architecture.md` を参照。

## Frontend

UI変更時は `docs/frontend.md` を参照。

## Database

DB変更時は `docs/database.md` を参照。

## Verification

変更後は最低限以下を確認する。

- lint
- typecheck
- test
- build
```

Codexに大量のルールを最初から読ませると、かえって重要な情報が埋もれることがある。

そのため、

```text
AGENTS.md
↓
必要なドキュメント
↓
必要なコード
```

という順番で読める形にする。

---

# 3. タスクを小さく分ける

AIは一度に大量のコードを書ける。

しかし、

```text
認証機能を全部作って
```

のような大きすぎる依頼は避ける。

例えば認証機能なら、

```text
1. 認証周りの既存構成を調査
2. 型・データ構造を追加
3. APIを実装
4. ログインUIを実装
5. エラー処理
6. テスト
```

のように分ける。

1つのタスクで変更する範囲が小さいほど、

- レビューしやすい
- バグ原因を特定しやすい
- Codexも文脈を理解しやすい
- 失敗したとき戻しやすい

というメリットがある。

---

# 4. 実装前に「完了条件」を決める

Codexへの依頼では、実装方法を細かく指示するより、

> 何ができたら完了なのか

を明確にする。

## 悪い例

```text
ログイン機能を作ってください。
```

## 良い例

```text
メールアドレスとパスワードでログインできるようにしてください。

完了条件:
- 正しい情報ならログインできる
- 間違った情報ならエラーを表示する
- ログイン後は /dashboard に移動する
- 既存の認証方式を利用する
- DB schemaは変更しない
- lint / typecheck / test が通る
```

---

# 5. Codexに最初に調査させる

いきなりコードを書かせない。

まず、

```text
このタスクに関係する既存実装を調査してください。

まだコードは変更しないでください。

確認するもの:
- 関連ファイル
- 現在の処理の流れ
- 再利用できる既存コード
- 変更が必要になりそうな場所
- 注意すべき既存仕様

調査結果と実装方針を簡潔にまとめてください。
```

と依頼する。

この段階で、

- Codexの理解が間違っていないか
- 余計な変更をしようとしていないか
- 既存機能を再利用できているか

を確認する。

---

# 6. 実装方針を確認する

Codexの調査結果を見て、人間側で次を確認する。

```text
□ タスクの目的を正しく理解している
□ 変更範囲が広すぎない
□ 既存機能を無視して作り直そうとしていない
□ DBやAPIへの不要な変更がない
□ 明らかに危険な設計になっていない
```

問題なければ実装へ進む。

---

# 7. 実装を依頼する

実装時の基本テンプレート。

```text
先ほどの方針で実装してください。

要件:
- 既存の設計を優先する
- 必要以上にリファクタリングしない
- 関係ないファイルは変更しない
- 新しい依存ライブラリは、必要性が高い場合だけ追加する

実装後:
1. 変更したファイルを確認
2. lintを実行
3. typecheckを実行
4. 関連テストを実行
5. 必要ならbuildを実行
6. 失敗したものは原因を調査して修正
7. 最後にgit diffを確認

最後に以下を報告してください。

- 変更内容
- 変更ファイル
- 実行した確認
- 残っている問題
```

---

# 8. Codex自身に検証させる

Codexが

> 実装できました

と言っても、それだけでは完了とみなさない。

コード以外の確認手段を必ず使う。

代表的なもの：

```text
ESLint
TypeScript
Unit Test
Integration Test
E2E Test
Build
Browserでの確認
ログ
```

例えばNext.js + TypeScriptなら、

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

など。

プロジェクトごとに、

```bash
pnpm check
```

だけで主要な確認をまとめて実行できるようにしておくと便利。

---

# 9. バグ修正では「再現 → 修正 → 再確認」

バグ修正は特に次の順番を守る。

```text
バグを確認
↓
再現方法を特定
↓
可能ならテストを追加
↓
テストが失敗することを確認
↓
修正
↓
テスト成功
↓
既存テストも実行
```

Codexへの指示例：

```text
まずこのバグを再現してください。

可能なら、このバグを再現するテストを追加してください。

そのテストが修正前に失敗することを確認した後、
実装を修正してください。

修正後は、
- 追加したテスト
- 関連する既存テスト
を実行してください。
```

これにより、

> たまたま動いた

ではなく、

> バグが再発しない状態

にしやすくなる。

---

# 10. 実装後にSelf Reviewをさせる

テストが通っても、そのまま終わらせない。

Codexに変更内容をもう一度見直させる。

指示例：

```text
今回の変更についてself reviewしてください。

確認項目:
- 要件をすべて満たしているか
- 不要な変更がないか
- 重複コードがないか
- エラー処理に漏れがないか
- 型安全性に問題がないか
- セキュリティ上の問題がないか
- 既存機能を壊す可能性がないか

git diffを確認して、
問題があれば修正してください。
```

---

# 11. 可能なら別のCodexにレビューさせる

実装したCodexとは別のコンテキストでレビューさせると効果的。

例：

```text
この変更をコードレビューしてください。

実装者とは別の立場として確認してください。

特に以下を見てください。

- 要件漏れ
- バグ
- エッジケース
- 型
- セキュリティ
- 不要な複雑化
- 既存設計との不一致
- テスト不足

問題がある場合は、
重要度と理由を説明してください。
```

その結果を実装側Codexへ戻して修正させる。

```text
実装
↓
レビュー
↓
修正
↓
再レビュー
```

の流れを作る。

---

# 12. CIを使う

GitHubへpushした後、人間が毎回手作業で確認するのではなく、

CIで自動チェックする。

最低限おすすめ：

```text
lint
typecheck
test
build
```

理想は、

```text
Codexが実装
↓
local check
↓
PR作成
↓
CI
↓
レビュー
↓
merge
```

という流れ。

CIが失敗したらmergeしない。

---

# 13. 人間が見るべき場所

AIに任せやすいもの：

```text
コード作成
単純な修正
テスト作成
Lint修正
型エラー修正
ドキュメント更新
コード検索
```

人間が判断すべきもの：

```text
本当にその機能が必要か
仕様として正しいか
UXとして使いやすいか
設計方針として妥当か
セキュリティ上許容できるか
大きな技術選定
```

つまり、

> コードそのものより「判断」に人間の時間を使う。

---

# 14. 同じミスを繰り返したら仕組みにする

Codexが同じミスを何度もする場合、

毎回、

```text
これはやらないでください。
```

と言い続けない。

例えば、

```text
UIから直接DBを呼ばない
```

というルールを何度も破るなら、

以下の順で強くする。

```text
1. AGENTS.mdに書く
2. 正しい実装例を用意
3. lintで検出
4. architecture testで禁止
5. CIで失敗させる
```

最終的には、

```text
ミスする
↓
自動検出
↓
修正
```

になるのが理想。

---

# 15. 技術的負債を定期的に掃除する

AIは既存コードを真似する。

そのため悪いコードを放置すると、悪い実装が増えやすい。

定期的に、

```text
unused code
重複コード
巨大ファイル
古いAPI
不要な依存
TODO
一時的な実装
```

などを確認する。

例えば1週間や1スプリントごとに、

```text
最近の変更を確認し、
以下を調査してください。

- 不要な重複
- 複雑すぎる実装
- 未使用コード
- 不要な依存
- 古いTODO
- 一貫していない実装

動作を変えずに改善できるものを一覧化してください。
まだ修正はしないでください。
```

と調査させる。

その後、小さい単位で修正する。

---

# 16. 並列作業は「独立した仕事」だけ

Codexを複数同時に使う場合、

同じ場所を触らせない。

良い例：

```text
Agent A: API実装
Agent B: UI調査
Agent C: テスト作成
Agent D: 既存仕様調査
```

悪い例：

```text
Agent A: auth.ts修正
Agent B: auth.ts修正
Agent C: auth.tsリファクタ
```

同じファイルを同時に触ると、統合が大変になる。

必要ならGit Worktreeを使って作業場所を分ける。

---

# 17. 1タスクの標準フロー

普段は次の流れを基本形にする。

```text
① Issue / 要件を書く
↓
② タスクを小さくする
↓
③ 完了条件を書く
↓
④ Codexに調査させる
↓
⑤ 実装方針を確認
↓
⑥ Codexに実装させる
↓
⑦ lint / typecheck / test / build
↓
⑧ Codexにself reviewさせる
↓
⑨ 別Agentまたは人間がレビュー
↓
⑩ CI
↓
⑪ Small PRでmerge
↓
⑫ ミスや知見をdocs / test / lintへ反映
```

---

# 18. タスク開始時テンプレート

毎回使えるテンプレート。

```md
# Task

## Goal

何を実現したいかを書く。

## Background

なぜこの変更が必要なのかを書く。

## Requirements

- 要件1
- 要件2
- 要件3

## Out of Scope

今回はやらないこと。

- 対象外1
- 対象外2

## Constraints

- 既存APIを壊さない
- DB schema変更禁止
- 新規dependency追加禁止

など。

## Done

完了条件。

- 機能Aが動く
- エラーケースBが処理される
- lint成功
- typecheck成功
- test成功

## Verification

確認方法。

- Unit Test
- E2E
- Browser確認
- Build
```

# 19. Codexへの最初の指示テンプレート

```text
このタスクを進めてください。

まずコードを変更せず、関連する既存実装を調査してください。

確認してください:
- 関連ファイル
- 現在の処理の流れ
- 再利用できる既存実装
- 変更が必要な場所
- 影響範囲
- 注意すべき点

その後、
実装方針を簡潔に提示してください。

まだ実装は開始しないでください。
```

---

# 20. 実装時テンプレート

```text
先ほどの方針で実装してください。

以下を守ってください。

- 必要以上に変更範囲を広げない
- 既存設計を優先する
- 関係ないリファクタリングをしない
- 既存コードを再利用する
- 必要なテストを追加する

実装後は、
- lint
- typecheck
- relevant tests
- build（必要な場合）

を実行してください。

失敗した場合は原因を調査し、
今回の変更が原因なら修正してください。

最後にgit diffを確認し、
変更内容と検証結果を報告してください。
```

# 21. レビュー時テンプレート

```text
今回の変更をレビューしてください。

以下を重点的に確認してください。

- 要件を満たしているか
- 要件漏れ
- バグ
- エラー処理
- エッジケース
- 型安全性
- セキュリティ
- 不要な複雑化
- 重複
- 既存設計との不一致
- テスト不足

問題がある場合は、

- 問題
- 重要度
- 理由
- 修正案

を示してください。
```

# 22. 完了前チェックリスト

## 要件

```text
□ Goalを満たしている
□ Requirementsを満たしている
□ Out of Scopeまで変更していない
```

## コード

```text
□ 変更範囲が必要最小限
□ 不要なファイルを変更していない
□ 重複コードが増えていない
□ 不要なdependencyを追加していない
```

## 検証

```text
□ lint成功
□ typecheck成功
□ 関連テスト成功
□ build成功（必要な場合）
□ E2E成功（必要な場合）
```

## Review

```text
□ git diff確認済み
□ Codex self review済み
□ 人間または別Agentのreview済み
```

## Git

```text
□ PRが大きすぎない
□ commit内容が分かりやすい
□ CI成功
```

# 23. この手順で特に重要な5原則

全部覚える必要はない。

まずは次の5つを守ればよい。

## 1. 大きい仕事を一気に任せない

Small Batchにする。

---

## 2. 「どう作るか」より「何ができれば完了か」を書く

Codexに実装方法を細かく指定しすぎない。

---

## 3. 実装前に調査させる

既存コードを理解してから変更させる。

---

## 4. Codexの「できました」を信用せず、テストで確認する

Verificationを必ず行う。

---

## 5. 同じミスを人間が何度も注意しない

テスト・Lint・CI・ドキュメントなどにルールを残す。

---

# 24. 最小構成で始める場合

最初から完璧なAI開発環境を作る必要はない。

まずは、

```text
AGENTS.md

+

Task Template

+

lint
typecheck
test

+

GitHub Actions
```

だけでも十分。

そこから、

```text
バグが増える
↓
Testを増やす

設計違反が増える
↓
Lint / architecture testを追加

Codexが迷う
↓
docsを整理

同じ作業を繰り返す
↓
Skill化
```

のように徐々に強化する。

# 25. 最終的に目指す状態

理想は、

```text
Human
│
├─ Goal
├─ Requirements
├─ Architecture
└─ Judgment
      ↓
    Codex
      │
      ├─ Explore
      ├─ Implement
      ├─ Test
      ├─ Fix
      └─ Review
      ↓
     CI
      ↓
 Human Review
      ↓
    Merge
```

という形。

Codexを単なる「コード生成ツール」として使うより、

> 調査 → 実装 → 検証 → 修正

まで担当する開発Agentとして扱う。

一方、人間は、

> 仕様・設計・判断・ユーザー価値

に集中する。

---

# 結論

Codexを使った開発で再現性を高めるために最も重要なのは、

> 良いコードを書かせることより、  
> 「正しいコードかどうかを確認できる開発手順」を作ること。

である。

基本形は、

```text
小さいタスク
↓
明確な完了条件
↓
既存コード調査
↓
実装
↓
自動検証
↓
Self Review
↓
第三者Review
↓
CI
↓
Small PR
```

と覚えておけばよい。

Codexを賢く使うというより、

> Codexが間違えても、間違いを検出して修正できる仕組みを作る

ことが、安定したAI駆動開発につながる。
