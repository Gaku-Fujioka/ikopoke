## 1. プロダクトの目的

友人・恋人・家族などの少人数で、行きたい場所・やりたいことを共有し、予定を作り、訪問後に思い出として残せるアプリ。

中心となる利用の流れ：

**候補を保存 → メンバーが反応 → 行く場所を決める → おでかけを計画 → 訪問を記録 → 思い出を見返す**

解決したい課題：

- 気になる場所がSNS、地図、メッセージなどに分散する。
- 誰がどこへ行きたいのか分かりにくい。
- 保存しただけで終わり、実際の予定につながらない。
- 訪問時の写真・メモと、もともとの計画が別々になる。

対象はまず本人とパートナーなどの少人数。一般の友人や家族でも使える表現・設計にする。初期の利用人数や保存件数は容量保証ではなく、開発・試用の想定として扱う。

## 2. 用語

| 用語 | 定義 |
|---|---|
| スポット | カフェ、公園、美術館、ホテルなど、具体的な場所 |
| やりたいこと | 陶芸、ドライブ、花火など、場所未定でも保存できる活動 |
| アイテム | スポットとやりたいことをまとめて扱う呼び名 |
| グループ | メンバーが候補・予定・思い出を共有する単位 |
| リスト | グループ内でアイテムを整理する分類 |
| リアクション | 訪問前の意思表示。「行きたい」「あんまり」 |
| 訪問後の評価 | 行った後の5段階評価。リアクションと混同しない |
| おでかけ | 複数の候補をまとめた計画と、その実施記録 |
| 思い出 | おでかけの写真・メモ・訪問先をまとめたアルバム |
| モック | 見た目や操作を確認するための仮データ・仮の処理 |

## 3. 対象範囲と段階

### 3.1 実装の段階案

「MVP」は一度の実装依頼を意味しない。下記は既存方針を整理した段階案で、現在の完成度を調べてからタスクへ分解する。

| 段階 | 目的 | 主な範囲 | 完了判定の提案 |
|---|---|---|---|
| P0 | 開発の土台を整える | 既存調査、要件確認、AGENTS.md、案内用docs、タスク分割、検証方法 | 参照先・実行方法・未決定事項・次のタスクが明確 |
| P1 | UIの流れを試す | 既存デザインに沿う画面、モック、画面遷移、主要状態 | 実APIなしで中心フローの操作を試せる。仮の挙動を明示 |
| P2 | 保存と共有を使えるようにする | 認証、グループ、リスト、アイテム、リアクション、コメント、アクセス制御 | 別アカウントで共有でき、別グループのデータは読めない |
| P3 | 予定につなげる | おでかけ、計画モード、カレンダー、記念日 | 保存した候補から予定を作成・編集できる |
| P4 | 訪問から思い出につなげる | 訪問記録、写真アップロード、評価、思い出編集 | 計画から記録・思い出まで実データで一巡できる |
| P5 | 外部連携を充実させる | 地図、Places検索・写真、位置情報、通知 | 個別の範囲・費用・制約を確認して受入条件を満たす |

既存手順では地図APIが予定機能より先だったが、本書では中心フローを外部APIなしで先に試す順序を提案している。地図を初回公開へ含めるかはQ-11で決める。P1のモック完成を、P2以降の保存・認証・共有の完成と報告しない。

### 3.2 後回しにする機能

既存仕様でMVPから除外：外部アプリの共有メニューからの登録、AI推薦、AI自動プラン、Google Calendar同期、高度な権限管理、独立チャット、SNS化。高度な通知も後回し。

個人リストからグループへの共有は将来検討。個人利用そのものをどう実現するかはQ-03で決める。

## 4. 機能要件

### F-01 アカウント・認証・アクセス範囲

既存設計ではSupabase Authを利用する想定。ログイン方式は未決定。

提案要件：

- ログイン・ログアウトができ、ユーザーを識別できる。
- データは所属グループのメンバーだけに公開する。
- API、DB、画像取得経路でもアクセス制御を行う。画面を隠すだけで済ませない。
- セッション切れ時にログインへ誘導し、可能な範囲で入力のやり直しを減らす。

受入条件：未ログイン、所属メンバー、別グループのメンバーを区別して動作する。他グループのIDや画像パスを指定しても情報を取得・更新できない。

要確認：Q-01、Q-02、Q-13。認証方式の未決定はモックUI作業を妨げない。

### F-02 グループ

既存仕様：複数グループを作成し、リスト・候補・リアクション・コメント・予定・記念日・思い出を共有する。MVPではメンバー全員が基本編集可能。

提案要件：

- グループの作成、選択、名前の編集、メンバー一覧の閲覧ができる。
- メンバー招待・参加を提供する。方式はQ-02で決める。
- 現在操作中のグループを明示する。
- グループ切替時に前グループのデータや入力先が混ざらない。
- 全員編集可能という方針から、グループ削除・メンバー除外の権限まで自動的に導かない。

受入条件：2アカウントで同一グループの保存結果を確認できる。別グループへの切替で対象データが切り替わる。招待の再利用・期限・退会後のアクセスは決定した規則どおり。

### F-03 リスト

既存仕様：グループ内で「カフェ」「東京」「旅行」など自由なリストを作成する。

提案要件：作成、名前変更、アイテムの分類、リストによる絞り込みを行える。未分類の候補も保存できる。

受入条件：分類後に一覧の絞り込みへ反映される。リスト削除時に訪問記録まで意図せず失われない。

要確認：1アイテムを複数リストに入れられるか、削除時に未分類へ戻すか（Q-04）。既存データ案の単一list_idは仮案として扱う。

### F-04 スポット・やりたいことの保存

既存仕様：次の情報を保持候補とする。

| 項目 | 内容 | 本書の入力方針案 |
|---|---|---|
| 種別 | spot／activity | 必須 |
| 名前・タイトル | 名称 | 必須。空白のみは不可 |
| グループ | 共有先 | 必須。作成時に確認可能 |
| リスト | 分類先 | 任意 |
| 写真 | 見返すための画像 | 任意。未設定時の表示を用意 |
| 住所・緯度経度 | 場所 | 任意。座標なしでも保存可能 |
| メモ | 気になる点、補足 | 任意 |
| 優先度 | 行きたい候補の優先度 | 段階数・初期値はQ-05 |
| URL | 店舗サイトなど | 任意。有効な形式を検証 |
| 外部Place ID | 外部サービス上の識別子 | 外部連携時に任意で保持 |
| 登録者・登録日時 | 作成履歴 | システムが記録 |

提案要件：手入力で作成・閲覧・編集できる。やりたいことは場所未定のまま登録でき、後から具体的なスポットにつなげられる。関連付けの方法はQ-06で決める。

受入条件：名前だけの候補を保存できる。保存後の再読込で内容が残る（P2以降）。二重送信で同一登録が重複しない。入力エラーは対象欄で分かり、通信失敗時に成功表示しない。

外部検索が利用できなくても手入力は継続できる。候補の削除・アーカイブはQ-07の記録保全ルールに従う。

### F-05 一覧・検索・絞り込み・詳細

既存仕様：スポットとやりたいことを閲覧・絞り込みできる。保存済みスポットを地図から選べる。

提案要件：

- 保存済み候補をタイトルで検索する。
- リスト、種別、訪問済み状態で絞り込む。その他の条件はUI調査後に決める。
- カードから詳細へ移動し、保存情報・反応者・コメント・計画への入口を表示する。
- 0件、検索結果0件、読込中、取得失敗を区別する。
- 戻る操作で絞り込みを保つことを目標とする。

受入条件：指定したグループと条件に合う候補だけ表示する。0件時は追加や条件解除へ進める。データが消えた詳細URLでも画面がクラッシュしない。

### F-06 リアクション・コメント

既存仕様：リアクションは「行きたい」「あんまり」。反応した人を表示する。アイテムごとに短いコメントを付ける。独立したチャットは作らない。

2026-10-18の採用内容（D-013）：リアクションの表示を「行きたい！」「そこまで」へ変更する。
1人1候補につき1つで、自分の反応だけ変更・取り消しできる。まず件数と自分の反応を表示し、メンバー名とコメントは後続とする。以下の提案のうち、この範囲だけ採用済み。

提案要件：

- 1人が1アイテムに持てる現在の反応は1つ。変更・取り消し可能。
- 未反応は「そこまで」と区別する（D-013で表示名変更）。
- コメントは投稿者と投稿日時を表示する。
- コメントの編集・削除権限はQ-02で決める。

受入条件：自分の反応を切り替えても件数が二重加算されない。他者の反応を自分の操作で変更しない。別アカウントの投稿・反応を再取得で確認できる。即時同期は必須とはせず、必要性を別途判断する。

### F-07 ホーム

既存仕様の候補：次のおでかけ、2人／みんなが行きたい、最近追加された場所、やりたいこと、近くの保存スポット。

提案要件：初回は「次のおでかけ」「最近追加された候補」「共通して行きたい候補」を中心にし、各カードから詳細へ進める。情報がない場合は候補追加や計画作成へ誘導する。

受入条件：選択グループのデータで構成され、日時や候補の変更が再取得後に反映される。

要確認：「みんな」の定義（全員か、一定人数以上か）はQ-08。近くの候補は位置情報連携の段階で導入し、位置情報を許可しなくてもホームを利用できる。

### F-08 おでかけの作成・計画

既存仕様：複数スポットを1つのおでかけにまとめる。候補の「計画へ」、おでかけ一覧、カレンダーの日付から作成できる。

計画モード：

| モード | 内容 | 確認項目 |
|---|---|---|
| 時刻指定 | 12:30などの具体的な時刻 | 入力した時刻が保存される |
| 時間帯 | 午前・昼・午後・夜など | 時間帯のラベルが保存される |
| 時間なし | 順番だけ | 時刻を入れずに保存できる |

提案要件：タイトル、日付、計画モード、候補の順序、メモを扱う。候補を追加・取り外し・並べ替えできる。計画から取り外しても保存元の候補は削除しない。

受入条件：3モードで計画を作成・編集・再表示できる。候補の順序が保持される。別グループの候補をID指定で混入できない。モード変更で入力済み情報が黙って失われない。

採用済み（D-017）：初期計画は単日の日付必須。3モードを最初から利用でき、切替時も入力済みの時刻と時間帯を保持する。登録済みの表示名を使って所属メンバーから参加者を選ぶ。複数日にまたがる旅行は未決定（Q-09）。

### F-09 カレンダー・記念日

既存仕様：ここいこに関係するおでかけ予定と記念日を表示する。記念日は毎年繰り返し設定可能。外部カレンダー同期はMVP対象外。

提案要件：日付から予定を閲覧・作成できる。予定の日付変更をカレンダーへ反映する。記念日のタイトル・日付・メモ・年次繰返しを扱う。

受入条件：対象日に正しい予定が表示され、詳細へ移動できる。年次繰返しの記念日が翌年にも表示される。

要確認：タイムゾーンと、2月29日の記念日を平年にどう扱うか（Q-14）。

### F-10 おでかけ中の記録・訪問済み

既存仕様：スポットごとに写真、メモ、感想、評価を記録する。行った候補は消さず「行った！」を表示し、訪問後に5段階評価を保存できる。

提案要件：

- 計画した場所について、実際に訪問したことを記録する。
- 再訪を扱えるよう、候補そのものと個々の訪問記録を区別する。
- 計画終了時に未訪問の候補まで自動で訪問済みにしない。
- 評価は1〜5、未評価は別状態にする。

受入条件：訪問後も候補が一覧に残る。再訪記録が過去の写真や評価を上書きしない。写真登録が失敗した場合に成功と表示しない。

要確認：評価を必須にするか、個人単位かグループ共通か、候補単独での訪問記録を許すか（Q-10）。既存資料には「5段階評価を行った後に保存可能」とあるが、必須条件かは確定していない。

### F-11 思い出・アルバム

既存仕様：おでかけ終了後、写真・メモ・スポットを時系列でアルバム化する。本・旅行雑誌のようなUIを目標とし、表紙・写真・メモ・表示写真の編集を検討する。

提案要件：

- 終了したおでかけから思い出を作成し、一覧・詳細で見返せる。
- 表紙・表示写真・メモを直接編集できる。
- 時系列を基本とした自動配置を用意する。紙面の完全自由編集は初期対象外。
- 写真がない場合にも表示を成立させる。
- 保存元の候補が変更・アーカイブされても、過去の記録を保つ。

受入条件：終了操作の再送で同じ思い出が重複生成されない。編集が再読込後も残る。他グループから写真を閲覧できない。スマートフォンでも本文や写真が切れない。

要確認：終了後の再開、時系列の基準、訪問先情報の保存方法、画像制限（Q-07、Q-12）。画像原本は未確認なので、具体的なレイアウトを本書で決め打ちしない。

### F-12 地図・外部検索・位置情報

既存設計：Google Maps／Placesを候補とする。保存済みスポットをピン表示し、詳細へ移動する。

提案要件：検索結果から必要な情報を確認して候補登録できる。位置情報は「近くを見る」など必要な操作時に取得する。座標のない候補は一覧で扱い、誤った位置にピンを置かない。

受入条件：選択グループの座標付き候補が表示される。API失敗、上限到達、位置情報拒否でも一覧・手入力が利用できる。

APIの料金、画像や場所情報の保存可能範囲、帰属表示、キャッシュ条件は本書では断定しない。接続前に採用サービスの現行公式資料を確認し、費用上限と方針を記録する（Q-11）。

### F-13 通知

既存仕様の低優先候補：場所の追加、リアクション、翌日のおでかけ。

アプリ内通知・メール・Web Pushのどれを採用するかは未決定。配信チャネル、許可の取り方、頻度、停止方法、タイムゾーンを決めてから実装する。通知を拒否しても中心機能は利用できるものとする。

UI参考資料は既存の`docs/ui/`または`docs/design/`を調べ、実際に存在する方へ案内する。画面名とファイルの対応を`docs/frontend.md`に記録する。新規に置く場合は`docs/ui/`を推奨。Stitch等のHTML／React原本は参考資料として区別し、アプリ本体へ一括上書きしない。

## 6. データと状態の設計条件

既存データモデルの候補：profiles、groups、group_members、lists、items、spots、reactions、comments、outings、outing_items、anniversaries、memories、memory_entries。

この一覧は採用済みテーブル一覧ではない。実装前に現在のスキーマ・migrationと照合し、論理モデルから必要な差分を設計する。

### 6.1 守る条件の提案

- グループに属するデータは、その所属を検証可能にする。子データは親経由でもよい。
- 他グループのitem、list、outingを相互に結び付けられないようにする。
- リアクションはアイテムとユーザーの組で現在値を一意にする。
- 更新者・日時など、共同編集の調査に必要な情報を保持する。
- 訪問済み状態と「非表示にしたい」というアーカイブ状態を混同しない。
- 繰り返しの訪問、訪問後の評価、写真の保存先は初期データ案だけでは十分に確定していない。必要に応じて訪問イベントの構造を設計する。
- 思い出の生成・予定の完了処理は再実行しても重複や中途半端な状態を残さない。
- 同時編集の挙動を決める。無言の上書きを避ける方法はQ-15で検討する。
- DB変更はmigrationで管理し、本番への適用をローカル作成と分ける。

### 6.2 おでかけの状態案

| 状態 | 意味 | 遷移案 |
|---|---|---|
| planning | 候補や日程を検討中 | upcomingへ |
| upcoming | 実施予定 | planningへ戻す／in_progressへ |
| in_progress | おでかけ中 | completedへ |
| completed | 終了、思い出を閲覧・編集 | 再開可否はQ-12 |

状態名は既存案を引き継いだが、日程確定条件・中止・取り消し・遡った記録の扱いは未決定。画面とデータの実装前にF-08〜F-11の対象タスクで決める。

## 7. 非機能要件案

以下は本書で追加した品質基準案。採用する数値は実装計画で確定する。

| ID | 項目 | 要件・確認方法 |
|---|---|---|
| N-01 | 使いやすさ | モバイルファースト。主要操作がスマホで完結する。まず幅360px・390px・PC幅で横はみ出しや固定ナビの重なりを確認 |
| N-02 | UIの状態 | データ画面ごとにLoading／Empty／Error／Successを区別。保存中の二重操作を防止 |
| N-03 | アクセシビリティ | フォームにラベル、操作要素に名前、キーボードのフォーカス表示を付ける。色だけで状態を伝えない |
| N-04 | アクセス制御 | 認証、DBの行単位の制御、Storageの制御を通じてグループ間を分離。非メンバーの直接アクセスをテスト |
| N-05 | 秘密情報 | 秘密鍵や認証情報を公開コード・クライアント・ログへ出さない。公開前提のキーも用途に合う制限を設定 |
| N-06 | データ保全 | 削除や退会の影響を明示。元候補の変更だけで過去の思い出を失わない。保存失敗を成功扱いしない |
| N-07 | 応答性 | 画像サイズ・一覧件数・リクエスト数を制御。数値の応答時間目標は測定環境とともに後で決める |
| N-08 | 費用 | 有料APIの導入前に呼出条件、上限、監視方法を決定。画像の無制限取得や不要なポーリングを避ける |
| N-09 | 保守性 | 既存コンポーネントを再利用。仕様・設計・コマンドの正本を整理し、同じ詳細を複数箇所へ複製しない |
| N-10 | 検証 | 変更に合うlint・型検査・関連テスト・必要なbuild／ブラウザ確認を行う。未実行は明記 |
| N-11 | 運用 | 開発・Preview・本番の接続先を区別。公開前にバックアップ／復旧方法、問い合わせ時に見るログを確認 |

## 8. 技術方針

既存資料にある方針：Next.js、TypeScript、Supabase（Auth／PostgreSQL／Storage）。外部地図はGoogle Maps／Places、ホスティングはVercelが候補。モックUIを先に確認して実データへ段階的に接続する。

バージョン・パッケージマネージャー・配備先は現行リポジトリを調べて確定する。添付手順にある`pnpm`の例だけを根拠にnpmから移行しない。新規プロジェクトの作り直し、依存の一括更新、DB再構築はこの要件定義に含めない。

URLに適した状態はURL、一時的な画面状態はReactの状態、保存データは永続層へ分けるという既存方針を尊重する。大規模な状態管理ライブラリは必要性を説明できる場合に検討する。

## 9. 開発・完了の基準

### 9.1 1タスクの流れ

1. 要件ID、今回の範囲、対象外、完了条件を決める。
2. 既存コードと関連資料を調べ、変更案を示す。
3. 実装方針を確認後、小さい範囲で実装する。
4. 関連する自動検証・必要な操作確認を行う。
5. 差分を自己レビューし、問題を修正する。
6. 別のAIまたは人間がレビューする。
7. PRとCIで確認し、人間の判断でマージする。

バグ修正は再現→必要な回帰テスト→修正→再確認。同じミスを繰り返したら、説明だけでなくテスト・lint・CI等で検出する仕組みを検討する。

### 9.2 完了報告に必要な項目

- 対応した要件IDと、実際にできるようになったこと。
- 変更ファイルと変更範囲。
- 実行したコマンド、成功・失敗・未実行、その理由。
- ブラウザで確認した操作、未確認の操作。
- 残る問題、モックの部分、実API未接続の部分。
- レビュー状況とCI状況。ローカル成功だけでCI成功とは報告しない。

### 9.3 中心フローの受入シナリオ案

P4までの最小構成を対象とする。未決定事項の採用後、これをE2Eまたは手動確認へ落とし込む。

1. ユーザーAがグループを作成し、Bが参加する。
2. Aがスポット、Bが場所未定のやりたいことを保存する。
3. Bがスポットに「行きたい」とコメントを付け、Aが確認する。
4. グループの候補からおでかけを作り、順序を編集する。
5. 別の計画で時刻指定・時間帯・時間なしの保存をそれぞれ確認する。
6. 日付のある計画がカレンダーに表示される。
7. 実際に訪れたスポットだけ訪問記録を付け、写真とメモを保存する。
8. おでかけ終了後に思い出を開き、表紙とメモを編集する。
9. 再ログインしても内容が残り、グループのBから確認できる。
10. 無関係なユーザーCからは、詳細URL・データ取得・写真取得が拒否される。

加えて、0件・通信失敗・二重送信・セッション切れ・API停止・位置情報拒否・再訪のケースを対象機能に合わせて確認する。

## 11. 初回のAI作業範囲

最初は本書と開発手順を読み、既存コードとの対応・不足・矛盾を整理する。その後、別の指示で`AGENTS.md`を案内板として作成し、関連docsと小さいタスクに分ける。

初回の文書整備と、アプリ機能・テスト基盤・CIの実装を混ぜない。各段階の変更範囲と完了条件を確認してから次へ進む。
