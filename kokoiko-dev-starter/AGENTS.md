# AGENTS.md — ここいこ開発ルール

このリポジトリで作業するAIコーディングエージェントは、実装前にこのファイルと `docs/` の関連資料を読むこと。

## 1. プロダクトの目的

「ここいこ」は、行きたい場所・やりたいことを少人数のグループで共有し、リアクション、計画、おでかけ、思い出までつなげるモバイルファーストのWebアプリ。

中心体験は以下。

`行きたい / やりたい → みんなの反応 → じゃあ行こう → 日付と計画 → おでかけ → 思い出`

カレンダー、地図、記念日、アルバムはこの中心体験を支える補助機能であり、それ自体を主目的にしない。

## 2. 技術方針

- Next.js App Router
- TypeScript
- Tailwind CSS
- Supabase
- モバイルファースト
- Server Componentを基本とし、ブラウザ状態・インタラクションが必要な部分のみClient Componentにする
- 外部APIの秘密鍵をClient Componentへ埋め込まない
- DB変更は必ずmigrationとして残す
- SupabaseのユーザーデータではRLSを前提にする

## 3. UI実装ルール

- `docs/design/` のStitch画像を参考にする
- 画像の完全なピクセルコピーより、実際に操作可能で保守しやすいUIを優先する
- まず390px前後のスマートフォン幅で成立させ、その後レスポンシブ対応する
- 下部ナビゲーション、主要CTA、余白、カード階層を画面間で一貫させる
- タップ領域は小さくしすぎない
- 画像が未取得の場合でもレイアウトが壊れないようフォールバックを用意する
- 初期フェーズではモックデータを使用してよい

## 4. 作業範囲ルール

一度の依頼では、依頼された機能だけを変更すること。

禁止例：
- ホーム画面の依頼なのにDB全体を作り直す
- UI修正のついでに認証方式を変更する
- 要求されていないライブラリを大量に追加する
- 関係ないファイルを一括整形する

必要な追加変更がある場合は、実装前または結果報告で理由を明示する。

## 5. 実装前に行うこと

作業開始前に以下を確認する。

1. 関連仕様を読む
2. 関連する既存コードを読む
3. 変更予定ファイルを把握する
4. 受け入れ条件を確認する
5. 既存コンポーネントを再利用できないか確認する

## 6. 実装後に行うこと

利用可能なスクリプトに応じて最低限以下を実行する。

- lint
- typecheck
- build
- 関連テスト

失敗した場合は、隠さず原因を報告する。

結果報告には以下を含める。

- 何を変更したか
- 主な変更ファイル
- 実行した検証
- 残っている問題
- ユーザーがブラウザで確認すべき操作

## 7. Git

- `main` を直接大規模変更しない
- 1つの機能または修正 = 1ブランチを基本とする
- commitは意味のある小さな単位にする
- `.env.local`、APIキー、秘密鍵、トークンをcommitしない

推奨ブランチ名：

- `feat/home-ui`
- `feat/item-list`
- `feat/supabase-auth`
- `fix/mobile-nav`
- `refactor/item-card`

推奨commit例：

- `feat: add mobile home screen`
- `feat: add item detail page`
- `fix: prevent bottom nav overlap`
- `refactor: extract spot card component`

## 8. DB・Supabase

- DBスキーマを変更する場合は `docs/data-model.md` を確認する
- 本番相当データをSQLへ直書きしない
- RLSなしでユーザー所有データを公開しない
- `service_role` 相当の秘密鍵をブラウザに渡さない
- Storageにも適切なアクセス制御を設計する

## 9. 外部API

Google Maps / Places等は、UIモックが成立してから接続する。

導入時には以下を分離する。

- 表示用地図
- 場所検索
- Place Details
- 写真

料金やAPI仕様に関わる実装では、現行の公式ドキュメントを確認してから進める。

## 10. 不明点

仕様に曖昧さがあっても、勝手に大規模な仕様を追加しない。
小さく安全に実装できる合理的な仮定は置いてよいが、その仮定を結果報告に明記する。
